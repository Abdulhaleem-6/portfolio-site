02

Positioning

Pick the thread that runs through every repository, not the one that lists the most technologies.

The thesis: determinism under non-determinism

I looked for what your hardest commits have in common, and it is not a stack. It is a class of problem. In every codebase you were the person who took a system that could produce a different answer each time it ran and made it produce the same right answer:

  • Worknet AI — an agent claimed it had updated a field it never touched. You made the DOM executor report from a final page snapshot instead of from its own intentions, and surfaced sub-agent failures the model was hiding. (fix(chat-server): stop the DOM executor claiming updates it did not make)
  • Worknet AI — clicks fired into a still-rendering DOM. You gated actions behind waitForDOMQuiescence: a MutationObserver with a 120 ms settle debounce under a 1,200 ms ceiling, plus stable data-aid element identity so a re-render doesn't lose the target.
  • SmartFetch — 57 utility portals, each redesigning without notice, behind MFA. You made document identity content-addressable so a re-run can't double-file an invoice.
  • Vascan — cache stampedes at 500 peak req. Your Redis service keeps an onGoingRequestLookup promise map so N concurrent misses become one database call, with pub/sub invalidation keeping every instance's L1 memory cache honest.
  • Vascan — duplicate merchant settlements. Bull queues plus database-level dedup across 10 Paystack webhook types.
  • Debt Tracker — a shared debt fanning into per-member child loans could half-succeed. One Prisma transaction, self-referential parent/child, no partial-split state possible.

That is the same engineer six times. It is a genuinely differentiated position: most people building agent products right now have never had to fix a thundering herd, and most people who have fixed thundering herds are not writing token-eviction policies. You are doing both, in the same year.

01 · Teaching an agent to tell the truth

worknet-ai-mono · /work/agent-runtime

The one-line hook

An AI agent that edits a live admin console reported success on changes it had never made. Fixing that meant rebuilding how the agent perceives, acts, and remembers.

The three problems, and what you actually built

  • It lied. The agent narrated its intentions as outcomes. You made the DOM executor derive its report from a post-action snapshot — a finalPageStateNote grounded in page, dialog, and custom-control values — and stopped it swallowing sub-agent failures. (9 commits on this alone)
  • It acted too early. waitForDOMQuiescence: a MutationObserver over documentElement resolving after 120 ms of stillness, capped at 1,200 ms so a busy page can't hang the loop; waitForDoubleRaf for paint; ensureDataAid stamping a stable 8-char identity so an element survives a re-render; buildClickTransition diffing URL / title / modal / focus before and after every click so "did that work" is measured, not assumed.
  • It ran out of room. heavyToolResultEvictor — an input processor that walks the message list and collapses tool results in place by rule: snapshots and screenshots keep only the latest, knowledge_search content goes stale after 3 turns, results over 1,500 tokens collapse to a head. It weights any result carrying a served-file attachment as heavy regardless of its text size, because a 25-token image manifest re-serves a real image every single turn.

02 · 57 portals that don't want to be automated

invoice-sync-mono · /work/smartfetch

The one-line hook

Utility companies don't have APIs. They have login pages, MFA emails, and redesigns nobody announces. SmartFetch fetches invoices from 57 of them on a schedule, and delivers them to systems that only accept traffic from one IP address.

The four decisions worth a paragraph each

  • Plugin architecture with codegen. Every provider is a directory: adapter.ts (Playwright), meta.ts, a Zod schema.ts, an icon. Sources are generated into typed client and server bundles, so adding the 58th utility never touches the platform. This is the decision that made 57 tractable.
  • Automated MFA. SES receipt rule → S3 → Lambda. mfa-email-processor reads envelope headers (received, x-original-to, delivered-to) for a per-task alias, resolves the task, and stores the code for the browser job mid-login. Lead the case study with this.
  • Static egress IP as a dedicated lane. Basware and friends allowlist by IP. Rather than route all VPC traffic through one address, you built an isolated path: SFTP Batch jobs on their own private subnets → dedicated NAT gateway → pre-allocated Elastic IP. Your own design doc gives the reason — "sharing the fixed IP across all VPC traffic is unnecessary and would expose the IP on other outbound calls." That sentence is the whole case study.
  • Multi-tenant identity without per-tenant pools. cognito-enhancer handles pre-token generation: look up every tenant for the email, honour a requested tenant from clientMetadata or a pending-switch record, inject the claim. One user pool, N tenants, tenant switching without re-auth.
Stack
AWS CDK, Lambda, Batch, Fargate, EventBridge Scheduler, DynamoDB, S3, SES, Cognito, KMS, Secrets Manager, CloudFront, Playwright, Zod, Pino; React 19 + Vite + Chakra + TanStack Query + AG Grid
Scope
232 commits, second of fourteen contributors
Also yours
Tag-driven release system — any engineer spins a full isolated stack with is-devops release create private-myfeature; every resource stage-prefixed
The artefact
A redacted provider adapter — 40 lines showing the contract a new utility must satisfy

How to show it — not a screenshot

An infrastructure diagram you can point at in an interview, and a "what breaks" table: for each failure mode (portal redesign, MFA timeout, duplicate invoice, IP block, cold start) name the mechanism that catches it. 03 · Money that only moves once

Vascan-Api · /work/vascan

The one-line hook

A marketplace where one cart pays several galleries, a webhook can arrive twice, and 500 concurrent requests must not become 500 database reads. Four years, 541 commits, still in production.

The two mechanisms to show

  • The three-tier cache. getOrFallback checks a process-memory L1, then Redis L2, then the database — but the part worth showing is onGoingRequestLookup, a promise map that collapses concurrent misses for the same key into a single in-flight fallback. A dedicated pub/sub channel invalidates L1 across every instance, because process memory is the tier that silently goes stale. Reconnect uses capped exponential backoff. This is the thundering-herd fix, and it is twelve lines of genuinely good code.
  • The settlement engine. A multi-vendor cart groups line items by the organisation that owns them, resolves each organisation's Paystack subaccount, accumulates per-subaccount share and platform fee, and submits one split transaction — so each merchant is paid independently and the platform's cut is deducted once. Ten webhook event types (charge.success, transfer.reversed, refund.processed, subscription lifecycle) land on Bull queues with database-level dedup.
Stack
Node/Express/TypeScript, MongoDB, Redis (pub/sub), Bull + Bull Board, Paystack & Flutterwave, Pulumi, Docker, Sentry, Axiom, Jest + Dockest, AJV, AccessControl
Scope
541 commits · 443 TS files · ~34k LOC · 6 queues, 57 controllers
Range proof
Pair with vascan-creatives (Next 15 + Radix creator dashboard, 29 commits) to show you also ship product surface
The artefact
A sequence diagram of one duplicate webhook arriving twice and settling once

How to show it — not a screenshot

This one earns a small interactive demo: a button labelled "fire 500 concurrent requests", two counters — requests in, database calls out — and a toggle for the dedup layer. Off: 500 / 500. On: 500 / 1. It is thirty lines of client-side JavaScript simulating your own promise map, and it makes a caching story physical in a way no paragraph will.

04 · A debt that cannot split halfway

debt-tracker-api · /work/debt-tracker · public repo

The one-line hook

The only backend on this site you architected alone, start to finish — and the only one whose source a reader can open. That makes it the credibility anchor for everything else.

What to foreground

  • The self-referential loan model. One Loan row relates to itself through parent / splits, so a group debt fans into per-member child loans in the same table, created inside a single Prisma transaction. No partial-split state can exist. Show the schema — it is eight lines and it explains itself.
  • Notification fan-out done properly. A Notification holds the event; a UserNotification join table holds per-recipient isRead, keyed on [userId, notificationId] and indexed both ways. Twelve event types across two channels (Expo push, Postmark/Handlebars email) with per-user channel preferences. The design detail worth stating: read state belongs to the recipient, not the event.
  • The boring correctness. Global exception filter, request-level validation, Supabase-backed JWT via Passport, cron-driven due-date and overdue jobs, soft deletes throughout.
Stack
NestJS, Prisma, PostgreSQL (Neon), Passport/Supabase JWT, Expo push, Postmark + Handlebars, Render
Scope
106 commits · 12 modules · 44 endpoints · 8 models · 5.1k LOC
The artefact
Live Swagger/Scalar docs, plus the Prisma schema rendered as an ER diagram

How to show it — not a screenshot

Because this repo is public, spend the page on readable code. Two annotated excerpts: the split transaction, and the notification fan-out query. Link every claim to the exact file and line on GitHub. On a portfolio full of proprietary work, one page where a reader can verify you is worth more than three where they must take your word.

The case-study template

The Bostian collection is an index of ~1,970 portfolio links rather than a pattern guide, so I read the tier that consistently gets cited from it — agney.dev, akashrajpurohit.com, adamalston.com, andy-bell.design and their neighbours. The pattern that separates the memorable ones is unvarying: they narrate a problem, and the artefact is a diagram, not a screenshot.

Every case study on your site uses the same eight blocks, in the same order. Consistency is what makes a reader trust the third page after skimming the first.

BlockLengthJob
Hook1 sentenceThe problem in plain language. No stack names.
Context2 short paragraphsWhat the system is, who uses it, what "working" means. Your role, stated exactly — "second of fourteen contributors", not "led".
Constraint3–5 bulletsWhat made it hard. Constraints are the most under-used section in every portfolio; they are what make a solution look inevitable rather than lucky.
Architecture1 diagram + captionAn SVG you drew. Every box a real component with its real name.

The rule that governs every metric

Every number on the site carries its basis in the same sentence, or it comes off. "~25% inference cost reduction" invites "measured how?" — and if the answer is a shrug in an interview, the whole page loses its credit. Numbers you can source: commit counts, adapter counts, endpoint counts, LOC, event types, the eviction thresholds, the quiescence timings. Those are unarguable, and they are more persuasive than a soft percentage anyway.

Before you ship

Four things that could go wrong

  • Publishing employer detail you shouldn't. The SmartFetch and Worknet pages describe live client systems. Keep to architecture, name no customers, quote no proprietary source beyond short illustrative fragments, and get the yes from Phase 1 first. Your own design docs are employer property too.
  • Overclaiming ownership. You are second of fourteen on SmartFetch and one of several on Worknet. Say so, plainly, in the role line. A reader who discovers an inflated claim discounts everything else on the page; a reader who sees "2 of 14 contributors, owned the SFTP target and the release system" trusts the rest completely.
  • Soft metrics under scrutiny. "~25% cost reduction" and "~65% fewer DB hits" need a basis or they need to go. Your countable numbers are stronger anyway.
  • Forks read as your work. ~/Desktop/Dev/Codygo also contains clones of Stagehand, browser-use and Agent-E — upstream projects you have zero commits in. Keep them off the site entirely; "studied the internals of Stagehand" is a sentence for an interview, not a portfolio card.

What success looks like

A staff engineer at a company you want to work for lands on the homepage from a Hacker News comment, reads the hero, opens "Teaching an agent to tell the truth", scrolls to the hard part, and thinks: this person has actually shipped an agent into production and knows exactly where it breaks. Nothing else on the site matters as much as that one page landing that way.
